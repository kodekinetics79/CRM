## 5. Extension seam (implemented)

`server/extensions.js` is the single installation point. `server/app.js` calls it twice:

- `installPublicExtensions(app,ctx)` **before** authentication, for unauthenticated surfaces under `/api/public/*`. These carry **no session cookie**: each request proves itself with an explicitly issued signed token, so browser CSRF does not apply and each module enforces its own rate, replay and size limits.
- `installExtensions(app,ctx)` after all existing services, receiving `db, list, get, create, put, validate, exists, audit, csrf, write, admin, transaction, collections, schemas, getSettings, versionCheck, updateSpecial, schoolYear, isTenantActive, recheckAccess, ownerAllowed, mfaStatus, tenantId, production` and the existing `services` (audiences, correspondence, workflows, hosted giving, marketing responses, Mailchimp sync, documents, events, receipts, peer fundraising, grants, reporting, reminders).

Each module may return guard callbacks that app.js already honours: `validateMutation`, `validateDeletion`, `hasConstituentReferences` (merge protection), `workspaceData`, `close`. Per-module options arrive via `createApp({extensions:{<module>:{...}}})`, which is how tests inject clocks and TEST_ONLY transports.

UI seam: eight workspace screens are routed, grouped and helped (`Messaging`, `RecurringGiving`, `AccountStructure`, `VolunteerPortal`, `EventPlanning`, `BoardPack`, `TenantAdministration`, `DataQuality`), plus two public pages at `/give` and `/volunteer`. Each workstream owns one CSS file under `src/styles/`.

## 7. Business invariants every workstream must preserve

1. Login role, constituent category and communication consent stay separate concepts.
2. One person keeps one identity and one financial history across every category; a person and an organization never merge into one physical identity.
3. Money is exact integer cents; financial history is immutable or corrected through explicit retained revisions.
4. No category, merge, report, import, campaign or automation may duplicate revenue.
5. Voids, corrections, receipts, acknowledgments and source versions stay traceable.
6. Contact preference is not marketing consent; importing a communication does not send it; preparing a receipt or message never claims external delivery.
7. Tenant status, role, source revision, consent and approval authority are rechecked **at final execution time**, not only at preparation.
8. AI may recommend or summarise only, and never posts gifts, sends messages, alters consent, merges identities, issues receipts or changes permissions.
9. TEST_ONLY transports and adapters never contact a real provider; production transports stay disabled without explicit configuration and authorization.

## 8. Risks carried in this run

- **Scope honesty risk:** a locally passing synthetic scenario is not buyer acceptance. Dispositions may move to Local only when the written acceptance scenario passes and evidence is referenced; `acceptedByBuyer` stays `false` throughout.
- **Financial correctness risk:** new giving and campaign attribution paths must reconcile to existing posted gifts once, never create income on preparation, and never bypass void semantics.
- **Consent risk:** a provider-observed subscription must never grant consent or clear a sticky denial; suppression stays sticky across rebinding.
- **Concurrency risk:** capacity, idempotency and version checks must hold under parallel requests, not only in sequential tests.
- **Persistence risk:** a Postgres boundary that is not the live store must be described as readiness, never as a completed migration.
- **Regression risk:** 982 existing tests encode current controls; none may be weakened or deleted to obtain a pass.

## 9. Proposed acceptance tests (per capability)

Every capability must demonstrate, in its own tests: allowed role; denied role; tenant isolation; stale version or changed authority at execution; restart persistence; failure atomicity (no partial financial or ledger state); exact integer-cent values where money is involved; retained audit/history; accessibility of the matching screen; desktop and mobile journeys for the primary path; and no provider side effect in TEST_ONLY mode.

Additionally per workstream:

- **Messaging:** consent and suppression respected at send time; transactional vs marketing classification; recipient snapshot immutability; idempotent retries with bounded attempts; delivery/bounce/complaint/unsubscribe events recorded without claiming human readership; nothing sent without an explicitly configured transport.
- **Giving:** pledge vs recurring distinction; webhook signature verification and replay defence; one posted gift per settlement; refund/dispute/cancellation states; failed-payment recovery; donor self-service scope limits.
- **Programs:** capacity races under concurrency; waitlist promotion; self-cancel retains history; reminder success/failure/suppression; checklist assignment visibility and unresolved identification.
- **Accounts:** location/function pair uniqueness; parent/child designation integrity; allocation and filter accuracy at representative volume with no double posting.
- **Reporting:** typed workbook and PDF outputs open and match source rows; privacy provenance rechecked at export; stale source refuses partial output.
- **Persistence:** identical repository behaviour on SQLite and PostgreSQL; transactional financial writes; tenant isolation; explicit forward migrations; restore verification.
- **Identity/tenancy:** invitation lifecycle; entitlement enforcement; separation of duties; suspension revokes sessions; MFA enforcement unchanged; federation boundary disabled by default.
