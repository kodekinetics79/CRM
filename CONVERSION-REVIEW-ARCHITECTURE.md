## Current conversion contract and actual capability

The normalized planner converts **constituents, designations and posted gifts**. It is not a NonProfitEasy-native parser or full historical conversion. It accepts at most500 rows across at most10 files; the UI stages one CSV per supported type. It requires explicit source identifiers, validates hierarchy/dependencies and exact decimal dollars/allocations, detects duplicates and rejects changed/missing previously mapped records. Administrator and CSRF guards apply to preview/commit. Commit replans against current dependencies inside `BEGIN IMMEDIATE`, creates records/source mappings, verifies new counts/cents/grouped controls, saves reconciliation and audits atomically. Same source/file key and exact input replay returns historical reconciliation without adding revenue.

These are genuine safeguards. They do not imply source inventory, all historical entity coverage, a final delta/cutover, imported attachments/contracts or actual buyer acceptance. Matrix C1 remains Partial; C2 remains actual source contracts conversion Missing.

The current record payload deliberately sets campaignId, pledgeId and grantId to null, pledge text empty and constituent contacts to an empty list (`migration.js`, `payload`). A source giftKind such as Recurring, Pledge fulfillment, Matching gift or Planned gift remains only a classification. It does not create a pledge plan, matching claim, fundraising association or recurring execution. Household string does not create rows in `households`/`household_members`. Gift date is retained, but createdAt/updatedAt are new Wimblo import times; source creation/correction/receipt-event chronology is not converted. Fiscal year is calculated under current policy; source-authorized fiscal reassignment is not mapped.

`sourceFiles` retains file number, collection, row count and column mapping. `content_hash` is a canonical normalized request fingerprint, not SHA256 of an original native export file. It does not retain original filename/export bytes/native format, source export timestamp/cutoff, source environment, custody approver or a manifest of attachments and exclusions. Source lineage reports accurately compare original imported record hashes with current records; replayed saved totals describe the historical import, not current financial balances. Those semantics should remain explicit.

For each actual export: stable source environment/name, export/cutoff time and timezone, original filename/format/byte count/checksum, native record count, source IDs/date range, approved protected-data categories, transform/adapter version and reviewer. Preserve the raw export in approved private custody or record an owner-controlled source archive reference; a public download URL is not custody. A project-level manifest should track expected batches and completion; existing per-batch atomicity is not an all-project transaction or cutover approval.

## Delta and cutover custody

Existing behavior supports exact replay and append-only new identifiers; changed existing source values deliberately reject as updates/merges unsupported. New fileKey is not permission to overwrite the same source ID. Thus a final delta needs an explicit approved action set: unchanged/reused, new, changed, void/correction, merged and deleted/tombstoned. Every action requires stable source identity/version or cutoff, current target version and conflict disposition. Per-type financial and consent transitions must use the business guard invariants; avoid generic upsert.

Use trial conversion in an authorized isolated workspace, record inventory coverage and reconciliation, resolve exceptions and prove recovery before promotion. Freeze or record all source/target writes at the agreed cutover watermark. Export initial and delta artifacts before the owner-reported November30 source-download cutoff; March access is not permission to download beyond it. Plan source/new-system use from November1 and reconciled core revenue/account-code/donor/basic-report readiness by November30, with explicit later accepted slices if applicable.

Cutover acceptance records the exact source manifest, adapter/contract version, expected/committed batch IDs, unresolved/excluded IDs, source/target counts and grouped financial/consent/file controls, current reports, responsible approvers and read-only old-system access/custody. Root's new `SOURCE-CONVERSION-CUSTODY.md` is the operational planning artifact; no implemented project-level manifest/watermark/delta approval exists now. An uncertain HTTP commit must first be resolved through saved batch history; exact replay already permits safe retry. A failed later batch leaves earlier successful batches committed. Do not restore a pre-conversion live database to undo them after unrelated legitimate writes; recovery/cutover rollback requires an approved isolated promotion or reconciled reversal plan.

## Governed disposition: separate workflow from conversion repair

The importer rejects changed or missing mapped targets and blocks deletion of mapped records. Documents, receipts, financial/correspondence/fundraising/event/tribute histories deliberately retain sources and snapshots. These controls are not a DPA disposition mechanism. Supplied DPA2.2 and4.6 require authorized access/copy/correction and agreed transfer/disposal, including specified60-day written-request/termination provisions and lawful/LEA-directed exceptions. Ten-year institutional history and these duties need category-specific approved retention/holds, not blanket destruction or blanket indefinite retention.

Governed disposition must include raw export custody, normalized staging files, current/mapped identities, private original/revision objects, immutable derived snapshots/native history, receipts/correspondence, logs and relevant recovery copies. Maintain transfer receipts, approval/scope/holds and non-identifying evidence of completion. A mapping hash alone is not a source export. Explicitly control how restricted/deleted data is handled during future restore so an accepted disposal is not undone. Do not disable retention triggers or cascade-delete operational history to unblock a migration conflict. Automated purge is a separate governed product slice, currently absent.

## Transaction and performance boundaries at the allowed row cap

- The in-progress planner now loads each supported collection once and indexes duplicate comparison; keep its previous case/trim/error-precedence/reused-source semantics and full stale-dependency detection. The migration owner is testing this repair. No independent measured performance conclusion is offered here.
- `dependencyHash` still hashes all supported current records, all source mappings in that tenant database and12 fiscal-policy samples.500 input rows does not bound existing history, memory/canonical serialization or read time. Current broad dependency invalidation safely requires another preview after unrelated supported-data changes; reducing it needs explicit duplicate/reference/policy/version coverage rather than a weaker digest.
- Core `app.js` validate checks gift externalRef with `list('gifts').some(...)`, including during each create under the commit transaction. Preview also calls the core validator for fully resolved references. Therefore eliminating planner scans alone does not remove repeated whole-gift scans: for B incoming gifts and G current gifts, this remains proportional to B×G (plus growing new rows). Potential CPU/event-loop/lock duration at buyer history is a concrete source risk, not a demonstrated outage. Any optimization must retain the shared core uniqueness invariant for ordinary CRUD/import and recheck atomically; migration-only checks must not become an alternate weaker rule.
- The transaction is synchronous `BEGIN IMMEDIATE`; hashes, record validation, source inserts, post-write grouped reconciliation and audit are inside its atomic boundary. Do not yield/await cloud file transfer inside it or return success before reconciliation/audit. Async file conversion needs staged private writes and the existing current-account/tenant/source/version checks before a short publication transaction, including durable ambiguous-write reconciliation.
- Large split allocations can mean up to100 allocations per gift; post-write control reconciliation resolves each account/source association. Current lookup by source/collection/record_id lacks a matching reverse composite index while the primary key is source/collection/external_id. A suitable reverse index is a bounded optimization subject to actual query-plan/testing evidence, not proof of buyer-scale readiness. Shared source maps may later need multiple aliases per target; do not add an unsupported unique reverse constraint accidentally.
- Imported batch results retain summaries, row outcomes/source maps and grouped control totals, not all original payload bytes. The keyset list already projects compact JSON in SQLite and avoids full list serialization of lineage. Batch detail loads one bounded batch; retain those distinctions. New history/file conversion must not inflate every list response with raw rows/BLOBs.

Meaningful next acceptance uses the supported500-row boundary against representative existing history and large valid allocation sets, confirms stale/duplicate/conflict and audit-failure rollback behavior, and measures preview/commit without sacrificing business invariants. Buyer10-year/archive size and operated recovery remain separate acceptance. No new tests or full suite/build were run by this review.
