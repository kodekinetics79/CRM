# Jordan Everbright controls and modular connectivity review

Review date: September 13, 2026. Scope: Kode Kinetics' local synthetic evaluator pilot tailored to Jordan Education Foundation, version 0.3.0. This is an independent source and contract review of the module connections and implemented guards. It is not district acceptance, a security certification, legal advice, a procurement submission or permission to use real student/donor data.

The critical control is that a module records the same underlying relationship and value that downstream modules report. Requests, awards, pledge commitments, recorded receipts, recognition, noncash valuations, event prices, volunteer hours and manually logged communications have different meanings. Joining modules must not change those meanings or confer new authority.

## Review findings and disposition

1. **Conditional legacy acknowledgment guard gap.** Current acknowledgments have two links: `gift.acknowledgment.communicationId` and `communication.giftId`. Communication identity/status/date/channel validation currently depends on `old.giftId`. A persisted legacy-shaped communication with the first link but no reverse `giftId` can be relabeled while its gift still declares the original completed acknowledgment. An isolated in-memory probe created an acknowledgment, removed only the reverse field to reconstruct that persisted shape, then submitted a current-version PATCH changing donor, Logged to Draft, date and channel; the API returned **200**. This is not a failure of the current acknowledgment creation path and does not establish that every existing database contains such a record. It is a migration/guard gap if earlier one-way acknowledgment records are retained. **Resolved:** validation now also finds gifts whose acknowledgment points at the communication, without requiring the reverse field or inventing an identity. An independent post-fix probe returned **409 for all four protected-field changes**, while an expanded factual body returned **200**. A permanent legacy/restart regression is a separate QA check; these probe results do not claim a completed production migration.
2. **Grant pipeline label conflates request and award.** At initial review `reportRows('Grant pipeline')` displayed `g.amount` beneath `Requested / awarded`. Phase three defines that field as requested funding only. A $25,000 request with a $15,000 award therefore exported $25,000 under an ambiguous financial label. **Resolved:** the pipeline header is now **Requested amount**. An independent post-fix helper probe showed $25,000 under that exact header for a record with a distinct $15,000 award. The Grant reconciliation report already distinguishes request, recorded award and receipts; unknown legacy awards are not replaced with requests.

Nonblocking connectivity observation: `GrantDetail` supports an optional direct “Record grant receipt” action, but `RecordDetail` does not supply its callback at initial review. The working path is Gifts → New gift → Grant revenue → named funder → Linked grant award. The optional shortcut should not be represented as available until wired and tested.

## Permission and authority matrix

| Action | Anonymous | Board viewer | Staff | Administrator |
|---|---|---|---|---|
| Minimal health / login | Yes | Yes | Yes | Yes |
| Read workspace records, reports, nonsecret organization/fiscal settings | No | Yes | Yes | Yes |
| Create/change/delete ordinary business records subject to reference/version/financial guards | No | No | Yes | Yes |
| Import/void gift, record acknowledgment, register/check in guest, clock/correct time | No | No | Yes | Yes |
| POST test feedback with valid CSRF | No | Yes | Yes | Yes |
| PATCH/DELETE test feedback | No | No | Yes, versioned | Yes, versioned |
| Read users/audit; create users; edit settings; download snapshot | No | No | No | Yes |

The server enforces these rules independently of hidden UI buttons. A staff task owner label, donor name, soft-credit attribution, typed tester name or completed grant stage does not grant application privileges. The feedback exception is confined to POST `evaluations`; it does not permit ordinary viewer writes. Viewer access includes donor contact/business records across the workspace: no field-level school/student segregation, tenant isolation or constituent self-service authorization is claimed.

## Cross-module integrity and provenance

- **Authenticated session boundary:** scrypt password hashing; random opaque cookie token stored hashed; HttpOnly/SameSite Strict cookie; eight-hour expiry and 30-minute idle timeout; CSRF on authenticated mutations; configured origin allowlist, bounded JSON and login throttling. Production requires explicit HTTPS origin/secure transport and explicitly trusted proxy; evaluator mode rejects production/nonlocal configuration. Health exposes only status/version/mode. Local demo credentials are public synthetic test access, not a production secret.
- **Identity and validation:** strict bounded schemas reject caller-controlled IDs, financial status, acknowledgment, registrations, clock metadata and other protected keys. Real calendar dates, positive integer money and consistent in-kind method are checked server-side. Collection UUID references live in JSON records and are checked in application transactions; this is not a relational FK constraint on every JSON reference. Direct database tampering is outside the authenticated API boundary.
- **Atomicity:** SQLite `BEGIN IMMEDIATE` wraps validation, relationship checks, write and audit. Import is all-or-nothing; gift acknowledgment and its communication, volunteer interval/aggregate and correction/aggregate are written together. Financial ceiling checks observe every posted linked receipt under the write transaction. No asynchronous database writes occur inside these synchronous transactions.
- **Version control:** generic update/delete, financial void, acknowledgment, clock and correction require current integer versions. Stale writes return 409; UI refreshes and asks the user to reopen the editor. Event membership operations and settings changes have transactional validation but do not accept caller versions. Financial records cannot be physically deleted or changed after void. Fiscal settings recalculate stored gift school years and increment gift versions.
- **Audit:** mutations record authenticated actor ID, operation, collection, record and timestamp in the same transaction; append-only triggers reject audit update/delete. Financial void reason remains in gift; correction audit includes previous/current/original hours and reason. Generic updates do not store complete before/after payloads, so this is operation provenance, not a full forensic change ledger. Workspace exposes latest 250 events to admin; admin snapshot includes the full audit. Database triggers do not certify resistance to privileged file modification.
- **Legacy upgrade:** preserve record identities and custom settings; upgrade exact old default brand only; retain prior volunteer hours once without invented dates; add missing grant award fields as zero/null, mark Awarded/Closed legacy values unknown in UI, and do not infer receipts from text/unlinked Grant gifts. Deterministic synthetic pledge seed is not duplicated. One-way legacy acknowledgment records now receive identity/status/date/channel protection by looking up the gift acknowledgment link, without inventing a reverse link or changing historical values.
- **Snapshot boundary:** admin snapshot omits passwords, hashes and sessions; it contains business records, user identities/settings and audit. It is an export, not evidence of encrypted managed backup, recovery rehearsal, retention enforcement or production disaster recovery.

Keep those approval gates separate from code test results and from self-entered client observations. The current review authorizes no external communication or procurement submission.
