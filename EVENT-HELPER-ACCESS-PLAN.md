# Restricted event-helper implementation plan

Read-only architecture review, September 13, 2026. No source changes, tests, deployments, account changes, or external actions performed for this review.

## Scope and acceptance boundary

`CURRENT-RFP-REQUIREMENTS-MATRIX.md:40,135` records four full users plus two optional nonadministrator board data-entry/event helpers if no added cost. It does not establish that every helper may read all donors or perform every staff entry operation. This first slice proposes **assigned-event ticket check-in only**. Board entry, registration, seating, ticket issuance, financial access, licensing and exact helper duties remain separate acceptance decisions. This slice alone cannot close the whole A8.3 criterion or establish buyer acceptance/pricing.

## Confirmed integration hazards

1. `server/app.js:59` currently admits only admin/staff/viewer. Simply adding a fourth authenticated role exposes `/api/workspace` at252, which serializes all ordinary business collections and settings. Existing module read endpoints are mounted before that route and are not protected by generic `write`. A local navigation filter is insufficient.
2. `server/eventOperations.js:69` returns raw event records and ticket/sponsor/auction financial views. Its `eventId` query is a filter, not an assignment authorization boundary. `ticketView` at61 includes constituent IDs, price, payment/gift references, balances, cancellation details, actor history and retained before/after snapshots. The normal ticket check-in route at75 returns that full view. Do not grant a helper that endpoint or reuse its response DTO.
3. The legacy `/api/events/:id/register`, `/checkin` and cancellation paths at `app.js:271–273` use constituent IDs and lack caller-supplied ticket/event optimistic versions. They return full events. The native event guard at `eventOperations.js:104` correctly prevents overwriting attendance where ticket history exists; this review does **not** claim that guard is bypassed. Legacy registration-only attendance is nevertheless a different workflow and must remain denied to the new helper.
4. `src/App.jsx:56` always fetches `/workspace` after `/auth/me`. Its global search at77 traverses business data, its `canWrite` at76 and create shortcut at63 use `role !== 'viewer'`, and most navigation at79 is not role filtered. A helper must never load that data or mount this staff workspace as its initial experience.
5. `server/mfa.js:14,23` has its own default three-role allowlist. Updating the app allowlist alone results in authentication/MFA inconsistency. Task ownership intentionally admits only admin/staff (`taskOwnership.js:8–9`); do not widen staff ownership, AI rechecks, grant/ask assignment or scheduled-report eligibility with the new role.

## Exact default-deny insertion point

Keep the existing global no-store/HTTPS/origin handling (`app.js:213`), login/MFA verification/logout and `/auth/me` (`224–228`), authenticated own-factor routes (`229–232`) and administrator enrollment-only guard (`233`). Immediately **after the guard at233 and before the first business module installation at234**, mount:

1. Dedicated `/api/event-checkin` router with its own helper/admin/staff policy and minimal response construction. The helper business surface is restricted to the exact routes below; no arbitrary method passthrough.
2. A central `/api` guard: any remaining authenticated request by `event-helper` fails403 with a fixed message and no data lookup. It covers unknown namespaces, methods and existing modules, including workspace, records, event operations, reports/exports/retained deliveries, receipt/document download, timeline, migration, backup, intelligence, evaluation and users/settings. Ordinary three-role behavior continues unchanged.

Own security routes remain reachable because they precede this guard. Public configuration must continue to contain only the existing public deployment configuration; no event data is added there. Existing OPTIONS handling is transport preflight, not permission to read or mutate business records. Do not base this gate on startsWith an arbitrary permitted prefix: install the concrete restricted router and then deny all remaining helper requests.

## Proposed restricted HTTP contract

All responses retain existing no-store policy. All event/ticket identifiers are strict UUIDs. All query/body objects are strict. Unauthorized/unassigned event or ticket lookups return a fixed404 without names, financial reasons or revealing another tenant's record existence.

| Route | Contract and projection |
|---|---|
| `GET /api/event-checkin/events` | Current active assignments only. `{events:[{id,name,date,location,version}],scope:'Assigned event ticket check-in only'}`. No full event object or notes. Proposed assignment limit100 is an explicit product bound, not a buyer requirement. |
| `GET /api/event-checkin/events/:eventId` | Strict query `{limit?:1..100,after?:UUID}`; stable ticket-ID keyset pagination with explicit `nextCursor`. `{event:{id,name,date,location,version},tickets:[{id,attendeeName,version,checkedIn,checkedInAt}],nextCursor}`. Only currently issued tickets with a surviving active constituent and current registration are eligible roster entries. No constituent ID is necessary in the client. Opaque ticket ID disambiguates identical names. Consistency failures never claim eligibility; report generic staff assistance without private reason. |
| `POST /api/event-checkin/events/:eventId/tickets/:ticketId/checkin` | Existing CSRF middleware; strict body `{version:positiveInteger,eventVersion:positiveInteger}`. Derive event and constituent from the native ticket; validate path event matches ticket, current helper assignment and account, both versions, issued/unchecked status, active surviving constituent and registration. Success `{event:{id,version},ticket:{id,attendeeName,version,checkedIn:true,checkedInAt}}`. No `ticketView`, event registrations array or payment query. |

No creation, editing, removal, restoration, reversal, ticket issuance, registration, seating, refund, checkout or message delivery is authorized. A revoked/suspended assignment cannot be used by replaying a previously loaded roster. Whether to add scan/opaque admission-code lookup, or expose a seating label, requires a separately reviewed scope; it is not necessary for this bounded first implementation. The ordinary ticket UUID is not a bearer credential.

### Mutation implementation

Factor a shared **native attendance transition service** out of `eventOperations.js:75` rather than independently duplicate check-in logic. Keep its `putAttendance` guard at56, event registration update/version bump, native ticket checked-in timestamp/version bump, immutable transition (`retainTicket:50`) and actor audit inside the same tenant SQLite transaction. The staff route can retain its full response; the helper route constructs a separate explicit allowlist DTO. Authoritative assignment/account checks belong inside that transaction. Do not catch financial lookup errors and then decide admission; financial views are absent from this path entirely.

Event-version conflicts across two different attendees are conservative existing concurrency behavior. The helper UI refreshes its restricted roster and invites retry; it must not auto-replay a mutation with newer versions. On ambiguous network outcomes, refresh the restricted roster and show the actual checked-in state before offering another action. No offline queue or optimistic success indication in this slice. Administrator reasoned check-in reversal remains the existing admin-only operation at78.

## Account, assignment and session integration

- Add `event-helper` consistently to app authentication, create/update user role schemas, and the explicitly supplied roles for the workspace MFA service. Keep admin-only account administration and last-active-administrator protection unchanged. A newly created helper has zero assignments and no business visibility.
- Store grants in the owning tenant DB, keyed by helper user/event with retained change history. Reject assignments to nonhelper/inactive users or nonexistent events. A user's tenant membership comes from the mounted tenant database, not a request tenant ID. Do not permit a platform administrator identity to function as an automatic tenant/helper session.
- Proposed admin API: `GET /api/users/:id/event-access` returning `{userId,version,eventIds}` for the current helper; `PATCH /api/users/:id/event-access` with strict `{version,eventIds:uniqueUUIDs(max100),reason:trimmedNonblank(max500)}`. Replace the active set atomically, retain grant/revoke history, increment the **user account version**, revoke that user's sessions and pending MFA challenges, and audit the reason. Stale version or audit failure rolls back grants, version and revocations. Reuse administrator CSRF and current account authorization. Existing `/api/users` already supplies version for account management.
- Do not infer an event-day/time restriction from `event.date`; assignment is the permission boundary. If expiry is added, it must be explicit, server UTC validated and rechecked on every read/write.
- Existing session `account_binding` includes role, active state and version (`mfa.js:11`, `app.js:217`). Assignment updates must bump that version; deleting sessions/challenges explicitly gives prompt revocation as well. Continue tenant suspension and account deactivation fail-closed behavior. Own MFA enrollment/recovery flows must work for the new role; enabled factors retain current challenge, recovery and replay protections. Mandatory helper MFA is an unconfirmed policy decision, not a newly inferred RFP requirement. If adopted, use one explicit role-policy predicate across login, enrollment-only access, disable and UI.
- Native full-database recovery fingerprints every table and clears restored sessions/challenges (`backup.js:27–36,116–126`), so added grant/history tables should be covered automatically. Add an exact roundtrip regression proving active grants/history survive while restored sessions do not. The ordinary JSON `/api/backup` is not a substitute for that complete native backup.

## Screen that drives check-in

Branch after `/auth/me` into a separate authenticated helper shell before `/workspace` is requested. Navigation contains Assigned events, Check-in and My account/security only. Clear all former staff workspace, deep-link selection, editor, search, notices and cached results on authentication/role/scope transitions. Direct links to staff pages resolve to the helper home without fetching their data. Keep logout and own account security accessible.

Present the event name/date/location, attendee-name search within the authorized roster, and one explicit Check in action. Names and opaque ticket references distinguish attendees; show authoritative checked-in state/time and a clear refresh/retry message on conflicts. Scope search to fetched assigned-event rows, disclose pagination, and do not claim that searching only the current page searches the full event. Either add a narrowly bounded server roster-name query with cursor tied to that query or show an honest current-page search label. Empty assignment state explains that an administrator must assign an event. Helpers cannot navigate to constituent details. Mobile touch targets, keyboard focus, disabled in-flight actions and status announcements are part of the restricted shell, rather than a visually reduced financial operations screen.

## Required focused acceptance tests

1. Parameterized helper default-deny across all currently installed namespaces, methods, unknown routes and direct deep links; assert no broad workspace request occurs in the helper frontend. Admin/staff/viewer regressions remain unchanged.
2. Poisoned financial/identity/actor-history marker values never occur in helper list, roster, success or error responses. Assert exact allowlisted keys and absence of constituents, email/phone/address/notes/relationships, prices, gifts, payments, balances, audit/history and document references. Own user name/email in `/auth/me` is intentionally self information, not donor exposure.
3. Unassigned event, wrong path event, other-tenant ticket UUID, unknown UUID, malformed ID, extra body fields and invalid/absent CSRF never change native records. Pagination is stable/bounded and cannot retrieve outside current grants.
4. A valid check-in changes precisely native ticket timestamp/version and event attendance/version, retains helper actor in immutable transition/audit, and changes no money/payment/receipt/seat record. Ticket cancellation, removed registration, merged constituent, stale ticket/event versions and duplicate/operator races fail atomically.
5. Audit failure rolls back both attendance representations, ticket transition and audit. Ambiguous client failure refreshes safe state and never announces unverified success or automatically replays.
6. Versioned assignment replacement/revocation, helper role change, user suspension, tenant suspension and pending MFA verification invalidate prior access. No historical staff payload remains in the helper UI. Own factor flow is supported; other-account factor/admin routes are denied.
7. Native recovery retains grant/history records but clears sessions/challenges. Existing last-active-admin, task/ask/milestone/report ownership restrictions remain enforced.
8. Four full users and two restricted helpers exercise allowed/denied journeys concurrently, including conflict and revocation. This proves the offered local behavior, not accepted commercial terms, buyer duties, hosted operability or a compliance certification.
